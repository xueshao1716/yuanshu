# 每日复盘方法

复盘不是流水账，目标是产出三样东西：**干净的归因、可复用的规则、暴露出来的留痕缺口**。
按下面的固定结构走，一段都不要跳——跳过哪段，哪段就会在下次以同样的方式再坑一次。

## 结构模板（六段）

1. **昨日主线与全景表**：挑 1~2 件重心任务展开（做了什么、根因是什么、留了什么待谁拍板），
   其余用一张表兜住（事项 / 状态 / 关键产出与证据）。状态只允许 ✅完成 / 🔄进行中 / ❌失败，
   禁止「应该可以了」这类模糊表述。
2. **逐件复盘**：每件事回答三个问题——坑在哪、根因链怎么剥出来的、沉淀了什么可复用套路。
   有环境认知（如「同一工具多份安装」「变量不展开」）单独点名。
3. **会话盘点 vs 记忆留痕落差**：列出昨日全部会话，逐条对照记忆日志。**没有留痕的会话直接写
   "无从查证"，禁止凭标题脑补"已完成"**；对可疑标题（例如用户表达不满的）单独标警。
   留痕不分技术含量：创作类任务（出图/视频/配音/文案）与排障同等对待，至少留
   流程约定、用的模型与技能体系、是否完整遵循用户红线、最终交付状态。
4. **做得好的**：只写可复现的行为（如"变量逐个隔离而不是瞎猜"），不写空泛表扬。
5. **不足与待办**：每条落到可执行动作（修什么、挂到哪跟踪、**写明决策人和两个以上可选路径**），
   不是「以后注意」。明确区分「回避了根修的悬空项」和「被动等待项」。
6. **一句话总结 + 今日第一动作**（例如先核 `git status` 工作区，防工作区漂移）。

## 归因规则

- 多层故障叠加时，按「读日志找第一个 failed/error」分层剥根因链，沉淀成**修复套路**而不是只修表象。
- **归因要排他**：引用的排障结论必须是隔离变量后的排他性结论（交叉验证 key/端点/DNS 解析器），
  不接受"可能是网络问题"这种含糊话。
- 系统自动行为与目标冲突时（如 UI 回写配置），**优先消灭行为的触发条件**，而不是对抗行为本身。
- 「超时 ≠ 失败」：拿到任务 ID 就说明还活着，先查状态再考虑重试，避免重复提交。
- 「想当然」类假设（环境变量会展开、路径相同等）第一天就验证。
- 用户抱怨质量（"变笨了"）必须与当日的故障/链路问题**关联诊断**，不许当孤立事件。

## 沉淀规则

- **口诀要趁热**：同一个坑第二次出现就必须当场升格为可执行判断规则
  （例：「中转站 `/v1/models` 返回 200 ≠ 渠道活着，必须真发一条 chat 才算数」）。
- 用户约定类信息：**当分钟落档**，多处冗余（固定记忆 + 纠正记忆 + 经验库），
  并主动回报「记在哪几处、复核过没有」；回复纪律与记忆纪律同时在线。
- 复盘中发现的新长期风险（如「升级后必复查被改过的配置文件」）直接追加进对应固定记忆区块。
- 任务涉及用户强调过的红线时，交付时**主动自证**执行是否完整，不等追问。

## 坑

- 悬空待办（CLI 版本不一致、插件适配等待）必须落到显式跟踪机制，不能只写在复盘文本里。
- 只复盘成功案例、跳过零留痕会话 → 落差表必须穷尽昨日所有会话。
- 复盘写成表扬信 → 每段"做得好"都要能提炼成下一步的做法。
- 待办只写"跟进" → 必须写明谁拍板、以及两个以上可选路径。
- 代价记录要诚实：纯运维/配置日没有代码提交是正常的，但开工先扫 `git status`。
- 聊天里的一句闲问往往是配置类任务的需求来源（用户需求与技术任务同源），复盘时把两者关联起来看。
