# 先验证，再交付

背景教训：一版视频没验证就宣布成功，用户一句"你怎么这么爱忽悠"点破信任缺口。
**所有产出先验证再交付，是默认流程，不是被打脸后的临时补救。**

## 三块铁律

1. **宣称 = 证据**。说出"字全对""渲染成功""链接可用"之前，必须有对应证据
   （HTTP 200、文件真实存在且可读、ffprobe/文件头确认字节流）。没有像素/多模态能力时，
   绝不能替用户"目视验收"图片。
2. **空输出 ≠ 成功**。工具返回空内容、或报 unknown tool（没装配）时，视为失败并立即如实上报，
   不得当成功带过。
3. **顺序不能反**：先宣称后补证是最高频的翻车模式（说"读完了/画好了"再拿后续动作找补），
   信任一旦崩了就补不回来。

## 验证清单（缺一不可）

1. **存在性**：文件存在且大小合理（不为 0 字节；视频通常应 >1MB）。
2. **可达性**：URL 返回 HTTP 200；本地文件可被读取。
3. **内容真实性**：不能只看 200 就下结论——下载后检查字节流（视频 `ffprobe` 读时长/编码，
   图片验文件头 magic number），确认不是错误页或截断流。
4. **完整落句**：回复正文必须完整收尾，不得停在半截话（输出被截断时宁可重发，不带烂尾交付）。

## 标准流程

```
生成产出 → 本地/HTTP 验证(200 + 大小 + 流/文件头) → 通过 → 才向用户宣布成功
                              ↓ 失败
        换参数/换模式重做（如 video 的 text↔reference、降分辨率）→ 重新验证 → 再交付
```

## 动手前的 4 步检查（批量出图/多步交付尤其要做）

1. **查工具装配**：本会话真正可用的工具清单先确认；没装配的工具不调用、不假装调用成功。
2. **查 shell 方言**：Windows cmd 没有 heredoc（`cat <<EOF` 必失败）；脚本一律用 write 工具落文件
   再执行，不内联；中文路径谨慎 `cd`，优先用工作区相对路径。
3. **查交付路径规则**：交付给前端的文件用工作区相对路径，不用 `D:\` 绝对路径（前端渲染不出来）。
4. **列 3-5 步计划再动手**：每步预判失败点与备选路径，不要把试错过程摊在用户眼前。

## 规则与坑

- **验证失败不隐瞒**：如实说"第一次生成流不对，我重做了一版并验过"，比假装成功可信得多。
- **降级要当场做**：依赖的配置/技能找不到时不要干等——用现有可用的跑，或明确告知
  "缺 X，我先用基础版替代"，别让会话停在流程中段。
- **不确定就标注**：内容里的假设（如"通用意象是假设"）要在交付时声明，
  它与"验证技术可用"是两回事，两件都要做。
- **安全红线**：涉及 key/token 的验证只探测可用性，绝不复述密钥本身。
- 图片中的文字（尤其中文竖排、花体）是重灾区：默认不可信——要么 prompt 里写死文字重跑，
  要么坦承可能乱码并说明验证手段。
- 验证失败后不要反复横跳换招：按预规划的路径切换，**一次只改一个变量**。
