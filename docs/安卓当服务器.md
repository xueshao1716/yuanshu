# 安卓当服务器：「全量离线包」可行性

> 2026-11-06 · 结论先说：**能，但分两条路，代价差一个数量级。**

## 一、需求拆解

「安卓手机当服务器」= 手机里跑起元枢的 Node 服务，局域网内其它设备（电脑/平板/另一台手机）用浏览器连它。

这需要三样东西：**Node 运行时 + 代码 + 后台常驻**。三者难度不同。

## 二、两条路

### 路 A：Termux（今天就能给用户）

**做法**：在 Termux 里装 Node ≥ 22.5，clone 代码，`node server.mjs`。

- 工作量：**半天**（脚本已写好：`scripts/android-server.sh`）
- 用户操作：装 Termux → 跑一个脚本
- 能力：**完整**。前端、记忆库（node:sqlite）、定时任务、通道都能跑
- 坑：
  - `node-pty` 在安卓上编译不了 → 只影响「终端面板」，其它照常
  - 安卓会杀后台 → 需要唤醒锁 + 关掉电池优化
  - 手机没公网 IP → 只能局域网用（要外网得配内网穿透）

### 路 B：打进 APK（真正的「安装包」）

**做法**：把 Node for Android（arm64）编进 APK，用前台服务常驻。

- 工作量：**两周起**，且有硬技术门槛
- 现状障碍：
  1. 主流方案 `nodejs-mobile` 停在 **Node 18**，**没有 `node:sqlite`**（那是 22.5 才有的）。要么换 `sql.js`(wasm) 重写存储层，要么自己交叉编译 Node 22+ for Android
  2. 需要写**前台服务 + 唤醒锁 + 存储权限 + 通知渠道**
  3. 代码本体（engine + 前端 + 技能）体积不小，APK 会到 60–100 MB
- 收益：用户双击安装就有服务器，不用 Termux

## 三、我的建议

**先给 A，把 B 当产品决定。**

理由：
- A 今天就能交付，用户马上能用
- B 的关键不是"打包"，是**"Node 22+ 跑在安卓上"**这件事本身，那是运行时选型问题，不是打包问题
- 如果用户群真需要 B，更聪明的做法是：**先用 A 验证需求**（有多少人愿意把手机当服务器），再决定要不要投两周

## 四、路 A 的验收标准

| 检查项 | 怎么验 |
|---|---|
| 服务起来了 | 手机浏览器打开 `http://127.0.0.1:8787` 能进 |
| 记忆库可用 | 系统页 → 记忆，能读写（验证 `node:sqlite`） |
| 局域网可连 | 电脑浏览器打开 `http://<手机IP>:8787` |
| 后台不被杀 | 锁屏 10 分钟后仍能连上 |
| 断电恢复 | 重开 Termux 再跑脚本，数据还在 |

## 五、已知限制（要跟用户说清）

1. **模型仍需联网**：元枢本身离线能跑，但模型调用走 API；要"完全离线"得接本地模型（另说）
2. **手机发热/耗电**：常驻服务会持续占用，建议插电使用
3. **不是所有安卓都能装 Termux**：部分厂商系统限制（华为/小米需要在设置里放开）
