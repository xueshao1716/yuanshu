# 元枢：系统诊断纠偏与质量基线

日期：2026-09-25。审查基于 2.116.1 / 7d605689。来源为桌面 `系统.txt`，以下以当前源码及本轮执行结果为准。

## 架构事实与处理决定

| 诊断判断 | 当前证据 | 本轮决定 |
| --- | --- | --- |
| React 是备份，vanilla 才是主界面 | `server.mjs` 的 `REACT_DIST` 和静态入口默认服务 `frontend/dist`；vanilla 仍有兼容入口 | 不重复“React 转正”，不删除旧入口 |
| 三套并行主引擎，应因产品命名而收敛 | `engine/engine-pair.mjs` 的缺省主次为 pi/yuanshu；配置可覆盖。SDK 不可用或通道非原生时可让元枢执行。dsh 标为不能主驾；`engine/gateway.mjs` 使用 `StandardAgentLoop` | 保留实际能力边界，切主驾须依据真实任务验收，不能由名字决定 |
| 没有版本同步机制 | `scripts/bump-version.mjs` 已同步九处声明及相关锁文件，存在契约测试 | 复用现有发版流程；本轮是质量基线，不虚构新客户端版本 |
| 没有审计/错误处理，应从零搭建 | 已有运行事件记录、review 验证证据、工具安全检查、轨迹及聊天错误事件 | 后续检查覆盖缺口和一致性，不把“已有”当成“覆盖完整” |
| 桌面端仅在计划里，没有分享能力 | `app/src-tauri/` 和分享工具实现已存在 | 多端一致性、分享可达性需按实际用户路径验收 |
| website-ai-first 一定仍失败 | 本轮完整测试中的对应测试通过 | 不修改没有复现的故障 |
| 应一次性将 server.mjs 拆到百行以下 | 生产入口仍是 `server.mjs`，包含启动、鉴权、状态与 SSE 等关联逻辑 | 优先建立可复现基线和真实路径验收，再小步抽离无状态路由 |

主工作区的未跟踪 `server-new.mjs`、`server/` 是未完成草稿，不是可部署替代品。本轮观察到不存在的 `getSessionList` 导出、聊天处理器调用签名不匹配、`json` 参数不匹配及硬编码旧版本等问题；保留这些用户文件，不加载到生产服务。

## 本轮落地

1. 复用 `scripts/verify-workbench.mjs`，增加 `npm run verify` 统一入口。单测、类型检查、前端构建分别落日志；任何一步失败，最终非零退出，后续检查仍可提供证据。
2. 测试工作空间、agent 状态、文件锁和工作记忆通过既有配置/注入接口指向临时目录；子进程环境不继承任意模型密钥、服务令牌或 `NODE_OPTIONS`。构建输出为 `tmp/verification-dist`，不覆盖线上前端。
3. 技能清单区分 Git 随附、本机附加和缺入口目录；实际技能仍全部参加契约检查，不通过忽略本机技能换取绿灯。
4. 主机三个本地技能仅修正 description 的触发说明：`boundary-subject-vs-stance`、`retro-ledger-audit`、`self-retro-review`。它们仍是本机未跟踪内容，不并入代码提交。
5. 技能目录按总预算缩短摘要，保留全部可激活名称，并将明确的适用条件前置，避免恰好截掉触发条件。43 个实际技能验证为 3991 字符，均保留触发语。若以后名称本身已超预算，应再设计分层目录；当前不宣称支持无界增长。
6. 移除测试对私人 `~/.agents/skills/ppt-html/SKILL.md` 的依赖，改为调用实际工坊处理器并检查交给执行器的 brief、动词、离线要求及无产物时的失败状态。
7. 新增 Windows / Node 25.8.2 CI：干净检出后安装锁定依赖，执行相同入口，上传检查证据；不含自动部署。`.github` 纳入证据指纹，工作流改变会使旧证据失效。
8. 更正 AGENTS 中清空 dist 的陈旧说明：当前 Vite 保留旧指纹文件，用于已有页面继续加载模块。

## 如何复验与读取证据

在项目根目录运行：

```powershell
npm run verify
```

安装依赖的干净环境先执行 `npm ci` 和 `npm ci --prefix frontend`。本轮本地 worktree 复用了主项目已安装依赖，不能等同于已验证远端干净安装。

| 文件 | 内容 |
| --- | --- |
| `tmp/review-verification.json` | 输入指纹、每步退出码/耗时/状态 |
| `tmp/verification-unit.log` | 全量测试及失败明细 |
| `tmp/verification-types.log` | 前端类型检查 |
| `tmp/verification-build.log` | 前端构建 |
| `tmp/verification-skills.json` | 仓库与本机技能来源清单 |

入口使用排他锁，防止并发覆盖证据。完成后输出保留的隔离目录位置，便于查错。正式状态由 `createReviewVerification().read()` 将当前输入与指纹比较后判定，不应只读旧 JSON 的 `passed` 字段。

隔离是应用配置级重定向，不是操作系统沙箱：不改写 HOME，不阻止任意未来测试访问绝对路径或网络。新增测试仍须审查文件操作与外部请求；CI 不配置生产凭据，也不安排付费模型任务。

## 后续阶段及验收门槛

首先做真实运行路径验收，逐次记录实际文本模型、媒体模型、执行引擎、首次事件耗时、完成耗时、终止原因、产物和结果。包含：

- 正常长任务、模型超时、空回复、输出截断、工具轮数上限；错误原因不能误标成模型不可用。
- 页面离开与重连、手机后台恢复；消息与图片不能重复，后台任务状态应与实际运行一致。
- 有副作用工具中断后续接；未知结果不能无条件重放，不能重复写入或重复收费。
- 工坊“想法 → 规划 → 分段生成 → 选区修改 → 交付”；失败保留已完成部分，不能恢复成无关默认页。

此前 Step-5 工坊长任务出现的两次 120 秒超时仍是待验事项。本轮本地单测不消除这个限制，不能宣称真实模型已稳定。真实模型验收通过后，再抽取无状态路由，每次比对状态码、鉴权、响应体；聊天/SSE 状态迁移最后处理。

本轮不实施暂缓的 OpenClaw/Hermes/曦/linxinyu 整合，不改默认主驾。
