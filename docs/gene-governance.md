# 人格基因治理与维护

适用版本：2.116.34。日期：2026-09-29。

## 正常链路

用户原始消息 → 保守关键词观测 → 短期 expression → 收轮检查候选 → 会话人工确认 → baseline 与审查记录一并保存。

- SDK 转统一通道沿用同一 turnId；同一会话、同一轮只计一次。持久去重最多保留最近 2000 轮。评测会话不写真实基因。
- 否定、请求、条件句及引用中的成功词不直接记成完成；扫描前 32000 字符。它仍是启发式，不是通用语义理解或人格测量。
- 中性消息可以没有观测事件，不应据此断定链路停摆。expression 按既有七天半衰期回归 baseline。
- 收轮只生成待审候选，不自动批准。自动候选需要同向偏离至少 0.1、至少三次带来源的观测、跨度至少 24 小时；最近有效样本不超过七天，事件保留窗口为三十天、最多 500 条。
- 同一基因已有 pending 时不重复生成。旧 auto_drift 提案继续保留待审并占据该位置，不自动驳回、不补造证据，也不保证次日就会出现新提案。

## 证据格式

批准时校验全部 evidence 项，而不是找到一条非 auto_drift 字符串就放行。数组最多 32 项，每项最多 4096 字符。

1. 自动观测：`gene-event:` 后跟实际事件 ID、时间、会话、标签、消息 SHA256、baseline 和 expression。必须精确对应存储事件、无重复，原时间区间仍满足连续来源要求。提案后的新观测不会仅因超过原区间而使旧证据失效。
2. 人工整理的文件：`source-file:<工作空间内相对路径> sha256:<64位小写哈希>`。仅允许非空且不超过 2 MiB 的 md/txt/json/jsonl；拒绝绝对路径、隐藏路径组件、目录穿越和指向工作空间外的符号链接或 junction。批准时重新读取并核对哈希。

哈希只证明来源字节一致，**不证明来源内容属实，也不替代人的判断**。观测保存消息哈希而非原文，需结合对应会话核查。不要把报告结论或“已获授权”字样伪装成真实互动证据。

## 审批入口

- `POST /api/genome/approve`：`{ sessionId, proposal_id }`。
- `POST /api/genome/rollback`：`{ sessionId, snapshot_id, reason }`，reason 必填。
- 沿用正常 API 鉴权；会话必须存在。请求在该会话发出 `gene-governance` 确认卡并等待最多 60 秒。
- 聊天页空闲时也接收确认卡；进入会话时可恢复仍在有效期的卡片，过期或切换会话后不继续显示。
- 用户须在服务所在电脑的本地入口确认（例如 `http://127.0.0.1:8787`）。确认走现有 `/api/agent/confirm`，远程/代理入口不能放行这两类敏感操作。
- 拒绝、取消、过期、目标在等待中改变均不提交。同一目标不能同时弹多张卡。确认仅用一次；核心落盘事务再次校验目标版本，防止确认后覆盖较新的变化。
- 不采用请求中自报的 reviewer 或 approved；审查人由实际确认生成：`human-confirm:<sessionId>:<confirmationId>`。

这些检查不是密码学意义的人类身份认证。能够执行本机代码、持有本机凭证或直接修改工作空间文件的进程仍在信任边界内；直接导入引擎不经过 HTTP 确认卡。不要把持有令牌、脚本写 reviewer 或文件哈希当成人工授权的证明。

## 回滚与存储

- 批准快照包含原 baseline、原 expression、应用后的 baseline 和提案关联；回滚只能针对该基因当前版本对应的、尚未使用的快照。
- 旧快照不能覆盖后续审批；即使数值绕一圈回到原值，版本链仍会阻止重复使用。缺少版本链的历史快照不自动迁移。
- 回滚恢复原表达，提案改为 rolled_back，并写入理由和审查记录；不是只改单个数值。
- 每次修改都在独占写锁内重读磁盘，不用过期内存覆盖文件；查询返回副本，调用者改对象不会污染引擎。
- genome.json 与 proposals.json 采用写前日志、逐文件原子替换和写后核验；失败尽力恢复两份原文件。读取先恢复未提交日志，不暴露半笔事务。只改观测时保持旧提案文件的原字节。
- 损坏 JSON、无效基本结构或写入失败会明确报错，不用默认值抹掉现场。

## 异常恢复与上线

写锁是 `工程/经验库/.gene-writer.lock`，写前日志是同目录 `.gene-transaction.json`。

进程异常退出可能遗留写锁。系统故意不按时间自动抢锁：先暂停写入、确认记录中的进程已退出且没有其他写者，备份两份数据及锁/日志，再由维护者处理遗留锁。**不要在进程仍活着时删除写锁，也不要先删事务日志**。解除确认过的死锁后，正常读取会尝试日志恢复；日志损坏或恢复失败须人工处理，不能声称自动恢复成功。

测试用临时工作空间和故障注入；全量验证用 `npm run verify`，不要对生产工作空间运行原始 `npm test`。服务端/引擎更新需重启实际 Node 服务；重启前确认无活跃任务，只定位本机监听实例，不批量终止 8787 的其他监听者（例如 EasyTier）。

本次为服务端治理修复，无原生桥或权限变更。既有客户端连接新服务即可使用修复；安装包自身版本不会因此变更，若交付标为 2.116.34 的新安装包，仍必须重新打包并验收，不能只重命名旧包。
