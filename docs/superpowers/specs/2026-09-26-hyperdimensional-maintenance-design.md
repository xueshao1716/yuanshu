# 元枢超维模式：授权维护与自我升级

日期：2026-09-26。状态：用户已批准书面规格，指定默认授权 1 小时；进入第一期实现，尚未授予权限。

## 1. 目标与取舍

让元枢在用户明确授权的任务范围内修改自身业务代码、维护指定电脑资源，减少范围内反复确认；用户仍掌握授权、发布与撤销权。

比较三条路线：直接增加无限权限档成本最低，但同进程代码可修改自身检查，不采用；继续逐次审批容易实现，但无法满足连续维护体验；采用独立授权控制面、限时能力与隔离执行，工程量较大但边界可验证，选此路线。

“超维”是用户授权的维护流程，不是高于所有规则的第四个数值档。禁止模型修改授权服务、审计、身份凭证、安全策略或自行续期。它不能突破 Windows 实际权限，也不关闭系统防护。

## 2. 实施前已核对的基线（本期修复见交付状态）

- `engine/sandbox-session.mjs` 提供 cautious / standard / trusted，映射三种应用内模式；会话日志没有授权到期机制。
- `engine/yuanshu-sandbox.mjs` 以工具名、命令规则和路径检查决定放行；它不是操作系统隔离。
- `engine/yuanshu-loop.mjs` 每次调用有政策和沙箱检查，但使用传入的模式快照，不能据此保证运行中撤销。
- `server.mjs` 的沙箱 GET/POST 缺会话编号时取 `latestSessionId()`；POST 直接写 `origin: human`，不能作为实际人工批准证据。
- `SandboxModePanel.tsx` 使用全局缓存键，`SandboxApi` 没有发送选中会话。界面的“本会话”与实际目标可能不一致。
- 现有沙箱阶梯只覆盖元枢自制循环，不代表 Pi SDK、外部执行器均受控。
- 工具安全模块还有独立拦截与受保护文件检查；超维不通过删除这些规则来实现。

以上是本次读代码的范围，不等同于对整个系统完成安全审计。

## 3. 分期与本次实现边界

本规格详细约定第一期：授权状态与协议、明确会话目标、能力可用性探测、撤销、审计接口和前端展示。第二、三期是依赖与验收约束，分别形成实施规格后再开发，不能把第一期标成“超维已完整可用”。

1. **授权基础**：修复会话目标；建立任务级授权状态机和控制面协议；没有合格执行器时显示不可用，拒绝激活。不得先接现有 unrestricted shell。
2. **隔离执行**：实现受限工作进程与用户拥有的授权服务；开放有限文件维护与代码副本修改、测试。隔离边界验证通过后才允许真实授权。
3. **受控发布**：不可变交付件、人工确认发布、健康验证、回滚与桌面包；再逐项扩充电脑维护能力。

不是本次目标：远程手机提权、自动升级安全核心、任意管理员命令、全盘清理、永久授权、切换默认引擎或重做整个工作台。

## 4. 信任边界与组件责任

- **元枢编排侧**：创建维护意图、展示进度、提交结构化动作；模型文本、工具参数、生成代码、构建脚本均视为不可信输入。
- **人工授权控制面**：独立于可自改的业务进程，拥有授权状态、策略、发布批准及审计存储；业务服务的 bearer token 不能签发维护权限。
- **受限执行器**：只能接收已核验动作，在独立权限身份/实际系统隔离内运行；不能读取用户主目录凭证、生产 token、控制面密钥，不能写控制面或生产源码。
- **发布执行器**：仅执行固定发布/恢复步骤；不接受模型提供的命令、脚本路径或任意可执行文件。
- **界面**：显示真实目标会话、任务、范围、到期时间、执行器状态及撤销入口；展示不等于批准。

不同进程但相同可写权限不算隔离。若业务服务继续以能够修改控制面的管理员身份执行任意代码，则不满足上线条件。第二期必须解决包括旧工具路径在内的可达越权通道，不能只给新工具加检查。

第一期以协议和受控测试替身验收，不宣称已经拥有上述操作系统边界；生产能力探测只能返回不可用，直到真实执行器提供验证证据。

## 5. 授权对象与生命周期

授权对象绑定 `leaseId / sessionId / taskId / runId / principalId / policyVersion / executorId`，记录规范化资源范围、动作集合、理由、签发与到期时间、撤销版本。租约编号不是凭证，模型不得获得控制面签名材料。

默认有效 1 小时，单次最长 2 小时；用户可选更短时间。跨会话、跨任务、重试产生的新 run、子代理、引擎切换均不继承。续期必须由用户重新确认，不能由模型模拟点击完成。

状态：`requested → active → expired / revoked / completed`，申请也可进入 `denied`；终态不能复活，重新申请产生新编号。请求超时、控制面失联、状态损坏一律拒绝执行。服务/控制面重启后旧租约不能自动恢复为 active。

每次动作接受前及实际开始前重新检查租约、动作摘要与版本；队列消费不能复用上一轮允许结果。到期不因持续运行自动延期。撤销后不得开始新动作；运行中可取消动作尝试停止并记录结果。已经写入的文件或完成的外部动作不声称被“撤销”，使用记录的恢复步骤。

发布切换若已进入不可分割步骤，撤销阻止后续新任务，由受信发布器收尾至确定状态或执行预授权回滚，不能停在未知的半发布状态。

## 6. 人工批准与接口契约

首版仅允许本机用户在受信桌面原生确认界面签发授权；浏览器/手机只展示状态与申请，不签发高权限。原生界面必须显示从控制面读取的真实摘要，不能渲染模型提供的批准页面。现有本地网页和通用原生桥不自动视为可信授权入口。

原生批准绑定一次性挑战、目标、范围、期限与动作/发布摘要；限制有效期与重复使用，验证调用方身份。网页传入 `origin: human`、普通 bearer token、跨域限制、自动点击均不能代替批准。

建议的业务 API 仅负责转发/读取，不持有签发密钥：

- `GET /api/sandbox/mode?session=<id>`：明确会话；缺失或未知拒绝，不猜最近会话。
- `POST /api/sandbox/mode`：要求已存在的 `sessionId`；维持原三档，不接受 `hyperdimensional` 映射为 danger。
- `GET /api/maintenance/status?session=<id>`：返回支持能力、不可用原因、当前任务与租约的非敏感视图。
- `POST /api/maintenance/requests`：明确 session/task/run、动作、资源与期限，仅创建待批准请求，无授权副作用。
- `POST /api/maintenance/leases/<id>/revoke`：核对用户会话权限；只收紧不放宽，重复请求幂等。用户还有独立原生撤销入口，不依赖业务服务存活。

不在通用 HTTP API 提供 grant/renew。第一期未接控制面时申请返回 `executor_unavailable`，不得生成可用租约。测试替身不可通过生产开关启用。

前端以 `['sandbox-mode', sessionId]` 分离缓存；无会话禁用变更。请求期间切换会话，旧响应不得更新新会话视图。旧档操作历史只能标为“界面/API 请求记录”，不能冒称已认证人工授权。

## 7. 动作边界与修改自身

能力采用结构化集合：指定资源读取、指定文件补丁、隔离验证、指定服务状态查询；后续服务重启仅接受用户批准的服务标识和固定实现。不存在 `arbitrary-command`、模型给定管理员脚本或任意路径启动能力。

规范化路径、重解析点、符号链接、硬链接及检查后替换均要在执行端防护；仅前缀比较不足。受限工作进程不得通过网络、IPC、继承句柄或环境变量取得旧高权限工具的权限。

代码编辑只进入隔离副本，不写正在服务的仓库；保留用户未提交改动。测试/构建脚本本身当作待执行的不可信代码；无生产凭据，网络默认关闭，必要依赖通过受控来源预置。不得在主用户身份下先跑构建再声称安全。

修改授权/审计/安全核心、发布器及其启动配置不属于自改业务范围，必须走独立人工维护。现有身份/人格等受保护内容也不因超维自动解除保护。

## 8. 发布与回滚约束（第三期）

发布前展示变更摘要、测试结果、受影响服务、当前基线与恢复点。批准绑定源代码、构建配置、依赖锁及最终交付件摘要；批准后任何内容变化都使批准失效。

发布器部署不可变交付件，不在生产执行候选的任意安装钩子。新版业务进程同样受限，不能借修改自身业务代码获得控制面权限。安全核心与业务运行权限的拆分是发布前置条件。

先检查真实运行任务；有任务时等待空闲或请用户明确接受中断。固定健康验证失败恢复原交付件，并验证恢复结果。回滚失败须明确显示“恢复失败、需要人工处理”，禁止循环重启或报告成功。

自改许可不等于 Git 推送、客户端安装或新建计划任务许可；按具体交付动作另列范围。Windows 提权由真实系统确认处理，取消/拒绝后停止，不换通道绕过。

## 9. 审计与异常呈现

控制面记录 request、grant、action-start、action-result、deny、expire、revoke、deploy、rollback；含序号、时间、会话/任务/运行号、批准摘要、资源摘要、结果与恢复状态。不记录密钥和无关文件正文。

日志在工作进程不可写位置，记录必须持久化才执行副作用；写入失败拒绝新动作。JSONL append-only 格式本身不提供防篡改保证。设置容量上限与轮转，满额不可悄悄丢弃关键事件。

拒绝原因分开显示：未安装、隔离不成立、未授权、过期、已撤销、目标不匹配、系统权限拒绝、执行失败；这些不计为模型不可用，不触发换模型绕过。

## 10. 验收标准

第一期必须验证：

- A/B 两会话读写互不串；缺失、未知会话拒绝；切换中旧响应不污染当前状态。
- 原三档兼容，计划模式仍只读；Pi/其他未接执行路径显示“不受本模式覆盖”。
- 申请不等于批准；伪造 human、普通 token、挑战重放、其他会话/run 均不能激活。
- 时钟边界、过期、重复撤销、重启、状态损坏、控制面断连均关闭执行；撤销与排队竞态有测试。
- 无执行器时按钮不可激活、API 拒绝，不能退回现有 shell；生产无测试授权入口。

第二、三期新增的上线门槛：

- 使用临时靶文件验证隔离进程不能触及控制面、凭证或范围外资源；含链接替换、间接脚本与旧路径调用，不以正则命中代替隔离验证。
- 用户批准确实发生在受信界面；系统拒绝不绕过；停止能终止可取消进程树，未终止时如实显示。
- 变更摘要漂移使发布失效；验证、发布、恢复各阶段注入故障，确认最终状态和审计一致。
- 不触碰生产资料完成测试；按仓库约定在隔离工作空间验证，前端构建不用线上 dist 作测试靶。

文档提交不运行全量程序验收；实现阶段必须分别提供测试/类型检查/构建证据，界面变更附实际交互验收。原生桥与权限变动必须重打桌面包；首版不提供手机提权，不因本设计承诺新手机包。

## 11. 交付状态

第一期已实现：显式会话沙箱 API、分会话前端缓存及异步切换保护；默认一小时、最大两小时的纯协议校验；只允许收紧的终态转换；关闭的生产维护入口与真实不可用说明。原有三个沙箱档位未放宽。

协议校验仅校验数据约束，不签发授权、不启动进程、不构成操作系统隔离。生产申请始终返回 `executor_unavailable`；无 grant/renew、环境变量绕过或测试授权开关。不存在租约时撤销返回 404，不虚报成功。

验证与分支状态见第一期实施计划。当前未部署、未重启、未推送、未打包；主目录用户改动保留。下一步进入隔离执行器与可信控制面阶段，不把本期协议与说明入口宣传为可用的整机权限。
