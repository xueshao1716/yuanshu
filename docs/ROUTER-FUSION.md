# 元枢怎么融合 Super-agent

> 对照物：DeepSeek Harness 团队 2026-10-31 的《Super-agent 设计探索》与开源原型
> [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT，研究原型，官方明确"不是产品"）。
> 本文只谈**怎么把它的架构思想融进元枢**，不谈直接部署原型（理由见最后一节）。

## 一、先对齐：我们已经有什么

| Super-agent 的零件 | 元枢现在的对应物 | 差距 |
|---|---|---|
| Router（常驻、轻量、只分派） | 无 | **缺** |
| Worker（上下文隔离、只干活） | `delegate_team` 子代理 / 独立会话 run | 有，但需要人发起 |
| 事件驱动（群聊/PR/CI 当输入） | 收件箱 `recvEvent`（邮件、钉钉、手动投喂） | 有入口，**没判断** |
| 程序层快筛 | 无 | 本次补上 |
| 语义层慢判 | 无 | 本次补上 |
| 订阅直通 | 无（子任务之间不共享事件） | 缺 |
| 上下文当缓存（内联/截断/链式召回） | 上下文压缩 `compactKeepArchive` + 记忆分层 | 部分 |
| 存算分离 | 会话持久化 + 运行在服务进程 | 部分（架构不同） |
| 外部 Watchdog（判断有无实质进展） | 服务看门狗 + 失败账本 + 交付门 | 缺"进展判定" |
| 异步工具 start/stop | `run_detached` + 后台任务池 | 有 |
| 验收环节 | **交付门（GREEN/YELLOW/RED）** | 我们比它多 |

结论：**我们不缺执行和验收，缺的是"谁来接第一棒、决定要不要做"。**

## 二、本次落地：最小路由器（Router MVP）

```
外部事件（邮件/钉钉/手动/以后接 GitHub）
        │
        ▼
① 快筛（不花钱）  来源白名单 / 去重 / 噪音 / 长度
        │ 通过
        ▼
② 慢判（轻量模型，agnes-3.0-flash）
   → ignore  ：不管（广告、闲聊、过期、重复）
   → ask     ：要人拍板（花钱/对外发布/删数据/改人格/权限）
   → dispatch：可以自己派人做
        │ dispatch
        ▼
③ 派活：注册一条 once 定时任务（+1 分钟），走**真实执行链路**
        │
        ▼
④ 执行 → 交付门判定 → 该推才推 → 决策台账可见
```

- 决策落 `记忆/运行时/路由决策.jsonl`（保留 500 条）
- 事务台「路由判断」：最近判断 + 一条输入框可手动投喂
- 接口：`POST /api/router/judge`、`GET /api/router/decisions`
- 入站事件（`POST /api/inbound/event`）成功后自动过一遍路由，不阻塞接收

**为什么用定时引擎派活**：它已经接好"跑一轮对话 → 写日志 → 推送"的完整链路，且受调度器约束，不用在请求处理路径里伪造 req/res 去调 `/api/runs`。

## 三、融合路线（三步，按风险从低到高）

### 第一步（本次已完成）：事件 → 判断 → 派活

验证"路由器不会乱派活"：

- 噪音（"收到"/"好的"）→ 快筛拦掉，0 次模型调用
- 技术故障（"CI 挂了"）→ dispatch，生成可独立执行的 task
- 涉及权限/花钱 → ask，不自己动手

### 第二步：Worker 隔离 + 订阅直通

- 每个 dispatch 开一个**独立会话**（而不是复用主会话），成功/失败都落交付门
- 同一事件源的后续消息（例如同一封邮件的回复）**直接投给处理它的会话**，不再回 Router
- 这一步需要给会话打 `origin=router:<eventId>` 标记，并让收件箱按 origin 路由

### 第三步：Watchdog（进展判定）+ 成本闸

- 每 N 分钟检查 router 派出去的活：有没有实质进展（工具调用/文件变更/交付门判定）
- 无进展 → 停掉并记失败账本，避免"跑了一小时什么都没干"
- 加**每日派活上限**与**预算闸**（`genesis`/`social` 权重已有类似旋钮，可复用）

## 四、明确不做的三件事

1. **不直接部署 dsh-superagent 原型到主力机**
   - 它要求 `danger-full-access`，Router/Worker 都以系统账号跑
   - 要求一个**专用 GitHub 账号**并轮询 Issue 评论
   - README 自己写着"研究原型，不是产品"
2. **不抄它的"自动合并"**
   - 元枢的红线（对外发布、改人格、删数据必须人点头）与自动合并冲突
3. **不做 Router 全权代理**
   - 我们的原则是"人的角色从操作员变验收员"，而不是"人退出"

## 五、度量（怎么知道融合有效）

不要只看"跑得快"，要能对照它给的三组指标：

| 指标 | 怎么量 | 元枢对应数据 |
|---|---|---|
| 完成时间 p50/p95 | 事件到交付的分钟数 | 路由台账 `at` → 交付门时间 |
| 人工介入次数 | 需要 ask 的比例 | `action=ask` 占比 |
| 单位事件成本 | token/事件 | 现有模型调用统计 |
| 误派率 | dispatch 后被交付门判 RED 的比例 | 路由台账 × 交付门台账 |

前两个现在就能出（路由台账已在记），后两个要等第二步把 runId 串起来。

## 六、一句话

Super-agent 那篇最有价值的不是它的代码，是把"人的注意力只有 3–5 个会话"当成**架构约束**来设计。
元枢的融合方向不是变成另一个 Super-agent，而是**把"要不要做"这一棒从人手里接过来，把"做没做好"这一棒继续留在交付门手里**。
