# 证据先行交付纪律

核心原则：**任何“已完成/已成功”的表述，必须以刚取得的证据为支撑**。没有证据就沉默或如实说“待验证”。

## 三条铁律

1. **宣称 = 证据**。说出“字全对”“渲染成功”“链接可用”之前，必须有对应证据（OCR/像素核验、HTTP 状态码 200、文件实际存在且可访问）。没有像素/多模态能力时，绝不能替用户“目视验收”图片。
2. **空输出 ≠ 成功**。工具调用返回空内容或未装配（报 unknown tool）时，视为失败并立即如实上报，不得当成功带过。
3. **生成类链接先验 200**。给用户任何生成结果链接前，先用可用的方式确认可访问，再回复。

## 动手前 4 步检查（尤其批量出图/多步交付）

1. **查工具装配**：本会话真正可用的工具清单先确认，未装配的工具不调用、不假装调用成功。
2. **查 shell 方言**：Windows cmd 无 heredoc（`cat <<EOF` 必失败）；写脚本一律用 write 工具落文件再执行，不内联。中文路径谨慎 cd，优先用工作区相对路径。
3. **查交付路径规则**：交付给前端的文件一律用工作区相对路径，不用 `D:\` 绝对路径（前端渲染不出）。
4. **列 3-5 步计划再动手**：每步预判可能失败点和备选路径（如：文字准确性 → 若 OCR 不过 → 改 prompt 写死文字重跑），不要把试错过程摊在用户眼前。

## 常见坑

- “先宣称后补证”是最高频翻车模式：说“读完了/画好了”再用后续动作找补，用户信任崩塌。顺序必须反着来。
- 图片中的文字（尤其中文竖排、花体）是重灾区：默认不可信，要么 prompt 写死文字重跑，要么坦承可能乱码并说明验证手段。
- 出图类任务先对照记忆中的技能红线（如人像默认走指定技能体系），越线前先说明理由。
- 验证失败后不要反复横跳换招：按预规划路径切换，一次只改一个变量。
