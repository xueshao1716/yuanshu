# 先验证，再交付

背景教训：一版视频未验证就宣布成功，用户一句"你怎么这么爱忽悠"点破信任缺口。补救版验证后才回复，成为标准动作。**所有产出链接先验证再交付，是默认流程，不是被打脸后的临时补救。**

## 适用范围
- 生成的图片/视频/配音文件的本地路径或 URL
- 任何告知用户"已生成/已完成/已可用"的产出物
- 外部资源引用（仓库链接、文档链接）在给出结论前至少确认可访问

## 验证清单（缺一不可）
1. **存在性**：文件存在且大小合理（不为 0 字节；视频通常应 >1MB）。用 `dir` 或 HTTP HEAD/GET 确认。
2. **可达性**：URL 返回 HTTP 200；本地文件可被读取。
3. **内容真实性**：不能只看 200 就下结论——下载后检查字节流（如视频用 ffprobe 读时长/编码，图片验文件头 magic number），确认不是错误页或截断流。
4. **完整落句**：回复正文必须完整收尾，不得停在半截话（输出被截断时宁可重发，不能带着烂尾交付）。

## 标准流程
```
生成产出 → 本地/HTTP 验证(200 + 大小 + 流/文件头) → 验证通过 → 才向用户宣布成功
                              ↓ 验证失败
              换参数/换模式重做（如 video text↔reference 模式、降分辨率）→ 重新验证 → 再交付
```

## 规则与坑
- **验证失败不隐瞒**：如实说"第一次生成流不对，我重做了一版并验过"，比假装成功可信得多。
- **降级要当场做**：依赖的配置/技能找不到时，不要干等——用现有可用的跑，或明确告知"缺 X，我先用基础版替代"，别让会话停在流程中段。
- **不确定就标注**：内容里的假设（如"通用意象是假设"）要在交付时声明，与"验证技术可用"是两回事，都要做。
- **安全红线**：涉及 key/token 的验证只探测可用性，绝不复述密钥本身。
