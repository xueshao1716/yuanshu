# 每日复盘方法

复盘不是流水账，目标是把当天的坑翻译成下次直接照做的规则。固定结构如下：

## 结构模板
1. **昨日工作全景**：一张表（事项 / 状态 / 关键产出与证据）。状态只允许 ✅完成 / 🔄进行中 / ❌失败，禁止「应该可以了」这类模糊表述。
2. **逐件复盘**：每件事回答三个问题——坑在哪、根因链怎么剥出来的、沉淀了什么可复用套路。有环境认知（如「同一工具多份安装」「变量不展开」）单独点名。
3. **做得好的**：只写有证据的（URL 验证 200、双路实测 alive），不写空泛表扬。
4. **不足与待办**：每条必须是可执行动作（修什么、挂到哪里跟踪），不是「以后注意」。明确区分「回避了根修的悬空项」和「被动等待项」。
5. **一句话总结** + **今日开工第一动作**（如先核 git status 工作区）。

## 归因规则
- 多层故障叠时，按「读日志找第一个 failed/error」分层剥根因链，沉淀成修复套路而非只修表象。
- 当系统自动行为与目标冲突（如 UI 回写配置），优先消灭行为的触发条件，而不是对抗行为本身。
- 「超时≠失败」：拿到任务 ID 就还活着，先查状态再考虑重试，避免重复提交。
- 「想当然」类假设（环境变量会展开、路径相同等）第一天就验证。

## 落档规则
- 用户约定类信息：当分钟落档，多处冗余（固定记忆 + 纠正记忆 + 经验库），并主动回报「记在哪几处、复核过没有」；回复纪律（不过度展开）和记忆纪律（真落档）同时在线。
- 复盘中发现的新长期风险（如「升级后必复查被 hack 的配置文件」），直接追加进对应固定记忆区块。

## 坑
- 复盘里提到的悬空待办（CLI 版本不一致、插件适配等待）必须落到显式跟踪机制，不能只写在复盘文本里。
- 代价记录要诚实：纯运维/配置日没有代码提交是正常的，但开工先扫 git status，防工作区漂移。
- 聊天里的一句闲问往往是配置任务的需求来源（用户需求与技术任务同源），复盘时把两者关联起来看。
