# 周期性自我复盘

适用场景：一天/一轮任务结束后的自我复盘，产出可核对的复盘报告 + 次日行动清单。

## 固定六段结构

1. **上次行动清单兑现核对**：逐条列出上次的行动项，每条必须给实证（文件路径+大小、exit code、grep 命中、验证脚本输出、字节数）。写不出实证的按「挂水分」处理，不许用"应该完成了"糊弄。
2. **会话逐单盘点**：表格两列「用户要什么 | 交付到哪一步」，逐会话过。用户末条悬空（没收到回复）的单独标出——这是最疼的欠账，优先级高于一切新任务。
3. **亮点**：只写可复制的做法（怎么验证的、怎么避的坑、当场提炼了什么模板），不写结果好坏本身。
4. **问题**：按疼的程度排序。排序依据：用户重复追问 > 直接提问悬空 > 质量事故（哪怕被验证拦住）> 安全卫生 > 流程绕行。
5. **记录里没有的**：显式列盲区。区分两类：「做了但没记录」和「根本没做」。拿不准就列出来待查，不假装知道。
6. **今天要做的**：JSON 行动清单，每条 {text, kind, due}。kind 分 fix（补欠账）/ verify（核查落地）/ improve（流程改进）。每条必须当天可动手、可验证完成。

## 挂账清单卫生（复盘时必查）

- 挂账条目必须有唯一标识；结清一项时**同步销掉所有同义旧条目**，否则清单出现「同一件事重复挂账」的水分（本次实测：显示 8 条挂账里 4 条是已结清项的旧影子）。
- 复盘时先去重再核销：拿挂账列表与已结清项逐条比对，归档重复条目后，剩下的才是真实欠账。
- 每笔挂账写清「欠什么 + 验证方式」；「交付物存在」和「验证通过」是两件事，只满足前者的算部分结清（如：条款写了但交付核查无证据）。

## 复盘产出要求

- 每条问题必须提炼成一条可入库的规则回写经验库，例：批量任务开场第一件事建检查点（不是断了再补）；同会话既有模式是最强意图信号；直接提问不许抛多种解读丢回用户，自己翻 git log/配置验证出唯一答案；敏感 key 引用一律打码（前8后4）；打包路径统一正斜杠、先对数据契约再写 UI。
- 行动清单禁抽象："改进断点续跑"不可执行，改成「批量任务开工第一步写 checkpoint 文件，续跑先读它再跳过已完成分片」。

## 常见坑

- 虚报兑现：核对以实证文件为准，记忆和印象不作数。
- 把「没记录」当「没做」：先查日志再下结论，查不到的如实进盲区段。
- 复盘只顾往后看：不提炼规则的复盘只是流水账，第二天还会踩同一个坑。
